## 1. Current item

### Today

There are three orderings, and none of them uses the frame time:

| Where | Current card at t | Used for |
|---|---|---|
| `app/store.py:63` `live_cards_from` | Live/edited cards at their latest version with `ts_ms ≤ t`, sorted by the `ts_ms` of each card's **first** version, newest first. A card shown again does not move back to the top. | `GET …/cards/live` (`app/main.py:131`, `contracts/README.md:43`), `/state` `live_cards` |
| `worker/brain/labels.py:118` `cards_at` | `live_cards_from(…)[0]`; previous = the other card with the latest first version | model context (`:297`), `resolve` (`:133`), `ask_which_item` options (`:364`) |
| `app/static/console.js:42`, `app/static/overlay.html:21` | Sorted by the latest version's `ts_ms`, so a seller price or a speech version moves a card to the top; the overlay also shows drafts | console list, overlay |

A card version's `ts_ms` is the time the version was written (`worker/brain/card.py:183` `partial`, `now_ms()`). That is after
the frame read, which takes p50 4.8 s / p95 6.2 s (D-021). So "live at t" is what had been recognised by t, not
what was on screen at t. PR #32 (draft) changes only the labeler's ranking. It waits for this spec and is not merged
today.

### Definitions (one, shared)

- **Appearance**: a card version whose `provenance.frame_ts_ms` differs from that card's previous version, the first
  version included. Its time is that `frame_ts_ms`. Today only `on_product_seen` writes a new `frame_ts_ms`
  (`card.py:208`, `:226`). Speech versions (`card.py:376-377`), seller prices (`app/cards_api.py:93`) and status
  bumps (`card.py:135`) copy the provenance, so a price, size or status change is not an appearance.
- **Appearance history**: every appearance of the session, sorted by (`frame_ts_ms`, `version`). It is built from
  card versions alone, with no new field and no new event.
- **Current item at t**: the card of the last appearance with `frame_ts_ms ≤ t`. The card's status is not part of
  the rule. **Previous item at t**: the card of the last earlier appearance that names another card.
- One function computes both, `current_at(versions, t) -> (current, previous)`. Proposed place: `app/current.py`.
  Users:
  - `labels.cards_at` calls it. This supersedes #32.
  - `GET …/cards/live?ts_ms=t` keeps its members (live/edited at the latest version with `ts_ms ≤ t`). It orders
    them by their last appearance at or before t, so the current item comes first when it is live.
  - The console list orders by last appearance. The overlay shows the current item at now.
  - The console and overlay read one small JS copy of the rule (`app/static/current.js`). The repo has no JS test
    runner, so the JS copy is checked against the Python test timelines in the browser (L2.5), not in `make check`.

### Watermark and the wait

- **Watermark W(session)**: the largest frame `ts_ms` such that every frame at or before it has been handled.
  A frame counts as handled when:
  - its read has finished, with or without a `product_seen`, or it was skipped on an error; and
  - the card version its `product_seen` causes has been posted.

  Frames are cut at 1 fps (D-021). W lives in the worker's memory. It is not an event, so the labeler and vision must
  run in one worker process, as `worker/__main__.py` runs them today.
- **Order comments wait; other labels do not.** The model is called at once, as today, with the cards known at the
  time. Only the attachment of an order to a card waits, through `resolve` and the order flow. The shield and the
  labels of questions, spam and scams are not delayed.
- An order comment at t is attached at once when W ≥ t. Otherwise it waits in a per-session queue that is bounded in
  time and in size, and is attached as soon as W ≥ t, to the current item at t.
- **Deadline**: `ATTACH_WAIT_MS` after the comment is received. It is set to the measured p95 from frame time to its
  card version on the live path (HQ estimate today: 4–5 s), is held in one place and is re-measured like H in D-025.
  Size bound: when the queue is full, the oldest comment expires early.
- **On expiry with W < t**: the order goes to `NEEDS_SELLER` with two candidates, the current and the previous item
  at t on the history known at that moment. The seller taps one; the customer is not asked. The customer is asked
  only for a missing variant, as today (`orders/flow.py:327-336`, `ask_variant`).

### Price

- The order is priced from the attached card only, never from the previous item's card.
- If the attached card's live version at t has a price, the order uses it and pins that version, as today.
- **If it has no price** (a draft):
  - no `order` event is written yet; the labeled comment waits in the flow;
  - when the card gets its first priced version, the flow drafts the order from that version, pins it, runs
    `orders/rules.py` unchanged, and sends the confirmation;
  - if the card is retired with no price, or the session ends, the order goes to `NEEDS_SELLER` ("no price").

  The waiting set can be rebuilt after a restart: it is the order labels with no order whose card has no price.
- **"No back-writing of the new item's price"** is read here as follows. Card versions stay append-only, and their
  `ts_ms` is the time of writing. A price never goes into an earlier version. A waiting order cites the later priced
  version it was drafted from, so the receipt carries that version. An order already sent is not repriced by a later
  version (pinning, as today).
- Today, an order on a card that is not live goes to `NEEDS_SELLER` (`orders/flow.py:316-318`, D-026). Under this
  rule it waits for the price instead.

### The four required tests

The times are media seconds. "Written" is the time a card version is posted.

1. **Quick switch.** A is shown at 10.0 and B at 12.0, which is under 3 s (C7). An order comment at 12.5 arrives
   while B's first version is still unwritten (written at 16.0).
   - The comment waits and is attached to B when W ≥ 12.5.
   - It never takes A's price.
   - B has no price, so the order waits for it, then confirms at B's price and pins B's priced version.
2. **A → B → A.** A (priced) is shown at 10, B at 20, and A again at 30, so A's card is bumped with frame 30.
   - A comment at 25 attaches to B. At 31, current = A and previous = B.
   - A seller price on B at 33 is not an appearance, so a comment at 34 still attaches to A.
   - `/cards/live?ts_ms=34000` lists A first, and the console lists A first.
3. **Price spoken before the card opens.** The line ends at 9.5 and A's frame is at 10.0; A's first version is
   written at 14.0. The line lands on A through the D-025 span `[frame − 1000, …)`, as today.
   - An order comment at 11 attaches to A.
   - If A's price is not yet written when W ≥ 11, the order waits and then confirms at that price.
   - It never takes the previous card's price.
4. **Comment right at a switch.** B's frame is at 20.0.
   - A comment at 19.6 attaches to A; comments at 20.0 and 20.4 attach to B.
   - If the read of the 20.0 frame passes the deadline, the comment at 20.4 goes to `NEEDS_SELLER` with the two
     candidates known then, and one seller tap sends the confirmation for the card chosen.

Each test is red on main before the fix. A 0 USD replay of test1 is run before and after the fix (reference correct,
proposals on the right card, `NEEDS_SELLER` count), with the afternoon session as the baseline.

### Known limits

- The frame grid is 1 s. A comment less than one frame before a switch attaches to the earlier item.
- At expiry, if the slow frame is the switch frame itself, the right card may not exist yet, so it is not among the
  two candidates. The seller can then reject.
- A wait adds up to `ATTACH_WAIT_MS` to the end-to-end time of order comments (C8). C8 is reported with and without
  the wait.

## 2. Stock hold (after the 30/10 gate; contracts PR, Founder merges)

- Today the hold is computed, not stored. Orders in `CONFIRM_SENT`, `CONFIRMED` and `CLOSED` hold stock
  (`orders/flow.py:27` `HOLDS_STOCK`, `held` at `:136`), and `CANCELLED` releases it.
- New rule:
  - an order in `CONFIRM_SENT` releases its stock 10 minutes after the confirmation was sent, or at the end of live,
    whichever comes first;
  - a cancel releases stock as today;
  - a receipt is sent only in `CONFIRMED`.
- Needs: a transition for the expiry, with actor, reason and a state or reason the Founder chooses in the contracts
  PR; a timer in the order flow; and a test that an expired order's stock is free for the next order and that no
  receipt exists without `CONFIRMED`. `orders/rules.py` invariants are unchanged.
- Estimate: about 4 h with tests, plus the contracts review.

## 3. Stock replies (after the gate)

- A `stock_question` gets an answer only when the item is certain (attached by rule 1, not expired) and the variant
  is certain (exactly one variant hit, as in `orders/flow.py:322-324`).
- The number is that variant's stock minus `held`, from the card's catalog data. It is never taken from speech or
  from the model.
- If either is uncertain, no answer is sent; the comment stays in the console.
- Needs: a `message_out` template (templates are free strings in `message_out.schema.json`, so no schema change) and
  the 24 h window check as for other messages.
- Estimate: about 3 h with tests.
